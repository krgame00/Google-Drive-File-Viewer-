# Completed video cache

The collapsed “คลิปที่เก็บไว้ในเครื่อง” panel sets the completed-video budget to off, 1, 2 (default) or 5 GiB. Its GB label uses the existing app's binary size convention. The budget covers cached completed clips, not the active OPFS download scratch file or other site data.

Only explicitly requested whole-file downloads are saved, after completion. A Cache Storage module stores payloads separately from lightweight size, modification-time and last-opened metadata. No OAuth tokens, API keys or upstream URLs are saved. Signed-in clips require the loaded profile and are scoped to its email; public clips use a separate scope. Explicit sign-out clears this cache, including pending saves. Cache reads validate available Drive size and modification time. HTML/JSON responses, incomplete transfers and clips exceeding the budget are not saved. A local playback failure removes that cached clip and retries streaming.

Opening a video checks the local cache before streaming, with a 350 ms lookup deadline so slow local storage cannot indefinitely delay the network path. Least recently opened clips are removed when space is needed or the budget is lowered. Turning caching off clears cached clips. Serialization and Web Locks (where supported) protect storage updates across tabs. Quota or storage failures leave ordinary playback available. The browser can evict cached data; file:// and browsers without Cache Storage use ordinary playback.

### Head-start cache (streamed clips)

The same budget setting also controls a second Cache Storage namespace, `gdv-video-heads-v1`: the service worker saves the opening chunk (up to 16 MiB) of every clip it streams, keyed by cache scope (signed-in email or public) with the file size, modification time and mime type. On the next open, or when seeking back into the opening seconds, the worker serves that range from disk with the same 206 headers it would synthesize from Drive and warms the next chunk in flight; when the page-vouched size or modification time no longer matches, the record is expired (30 days), dropped, and refetched. Setting the budget to off disables both saving and serving. A page-side admin handle lets the existing "ล้างคลิปที่เก็บไว้" button delete this namespace and its status line count head clips separately (LRU budget 512 MiB / 32 clips, enforced by the worker).

The player also asks the worker to prefetch the next episode's opening chunk while the current clip plays and when the Next-Up card appears, using the page's own token for that one file id. Prefetch is skipped when the cache budget is off, Data Saver (`navigator.connection.saveData`) is on, no cache scope is available, or the episode was prefetched this session; the worker answers `ok` and deduplicates concurrent requests. While a clip connects, the player shows its cached Drive thumbnail as the poster frame and removes it on first play so slice swaps never flash it.

Route failures are remembered in memory for five minutes per file and signed-in/public mode, with a bounded 200-entry map. Successful routes keep the existing seven-day preference. Explicit retry or reconnect clears the current file's cooldown. Whole-file loading remains manual; this is not a Google quota bypass or a guarantee of faster first downloads.

Verification: Node cache tests cover LRU eviction, metadata invalidation, size bounds, unavailable/quota-limited storage, logout/clear races, stale lookups, local playback failure and route cooldowns. `tests/video-cache-browser.html` exercises actual Cache Storage with a four-byte disposable payload in its own cache namespace. The in-app browser passed saving, reopening through a new cache instance, account isolation, byte accounting and cleanup. The settings panel was checked at 390 × 844; its content did not overflow. Full-size user video playback and throughput on the physical phone were not tested.
